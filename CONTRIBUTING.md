# Разработка и публикация CLI

Публичный продукт — Go CLI в `cmd/ssb/`: TXT-отчёт, исходные данные захвата и резолв имён. Внутренние отчёты, прототипы и прежний инструмент схем в публикуемый комплект не входят.

## Ветки и отдельная история

Публичная рабочая копия находится в `.local/publication/public-repository`. Клонируйте публичный репозиторий, не приватный проект. Не копируйте приватный `.git`, не связывайте хранилища через alternates и не переносите старые коммиты, внутренние ветки или теги. Первая публикация может начать новую историю без родителей; её состояние нужно согласовать до создания веток.

Перед созданием `dev` проверьте remote, публичный `main` и отсутствие уже существующего `dev`. Новый `dev` создаётся от публичного `main`; существующий не сбрасывайте и не пересоздавайте. Обычные PR направляйте в `dev`. Выпуск проходит через PR из `dev` того же публичного репозитория в `main`.

`push --mirror`, `push --all`, `--force`, `--force-with-lease` и обновление ref с префиксом `+` требуют отдельного поручения. Проверки и предыдущие разрешения на обычный push не разрешают эти операции.

## До PR

1. Сформулируйте проблему, наблюдаемый результат и границы изменения. Изменение должно быть достаточно небольшим для проверки и отката.
2. Проверьте форматирование, тесты, анализ и сборку:

   ```bash
   test -z "$(gofmt -l cmd/ssb)"
   go test ./...
   go vet ./...
   CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -buildvcs=false -trimpath \
     -o /tmp/ssb-check ./cmd/ssb
   /tmp/ssb-check --help
   python3 -m unittest discover -s tests -p test_publication.py
   ```

3. Проверьте поведение изменённого пути. Для захвата используйте контролируемый tcpdump или тестовую ВМ; тесты не должны захватывать рабочий трафик. Реальный захват и проверку на целевой ОС отмечайте отдельно от unit-тестов.
4. Передайте независимому агенту цель, базу и SHA изменения, diff, `REVIEW.md` и результаты проверок. Он проверяет логику и безопасность затронутых путей. Подтвердите замечания, исправьте причину и повторите нужные проверки. После первой проверки повторное ревью охватывает изменения и связанные пути; предел — три раунда.
5. В PR укажите результат, риск, подтверждённый SHA, проверки и способ отката. Решения человека о внешних действиях и чувствительных изменениях не подменяются одобрением агента.

CI проверяет маршрутизацию PR, публикуемый комплект, форматирование, тесты, `go vet` и статическую сборку. Правила защиты веток должны требовать успешный job `verify` и закрытые обсуждения; при новых коммитах проверки и необходимые одобрения актуализируются. Эти настройки включаются в публичном репозитории отдельно. Автоматический сервис AI-ревью требует собственной установки и доступа; данный workflow его не включает. Независимое локальное ревью остаётся обязательным до каждого PR.

## Перед публичным push, PR и подготовкой релиза

Работайте из публичной копии. Каждый раз проверьте remote, текущую ветку, все файлы комплекта, staged diff и отправляемые коммиты:

```bash
git remote -v
git status --short
git ls-files
git diff --cached --stat
git diff --cached
git log --format=fuller --stat origin/main..HEAD
python3 scripts/check-publication.py
```

Просмотрите полный diff каждого отправляемого коммита, включая удалённые позднее файлы, сообщения, авторов и адреса электронной почты. Диапазон определяйте относительно фактической принимающей ветки: обычно `origin/dev`, для первого `dev` и выпуска — `origin/main`. Перед отправкой другого локального ref проверяйте именно его. `.gitignore` не удаляет уже отслеживаемые файлы и не очищает историю.

`check-publication.py` проверяет явный список допустимых файлов, рабочие файлы, индекс и все коммиты, достижимые из выбранного ref. Он блокирует известные форматы секретов и запрещённые пути, но не определяет, является ли произвольный адрес, конфигурация или имя личными данными. Нужен просмотр содержимого. Значения найденных секретов в выводе не печатаются.

В `.git/info/exclude` публичной копии локально добавьте `/AGENTS.md`, `/.local/` и `/READY.md`. Убедитесь, что они не отслеживаются. Не публикуйте реальные конфигурации, серверные адреса, персональные данные, ключи, токены, резервные копии, внутренние планы и обсуждения. Разрешённые адреса в тестах должны быть явно синтетическими. Не копируйте готовые локальные бинарники и архивы в Git: собирайте выпуск из проверенного публичного SHA.

В локальном `.local/publication/READY.md` запишите SHA, состав комплекта, результаты проверок, итог независимого ревью, статус проверки приватных данных и способ отката. Это журнал подготовки, а не разрешение на отправку. Новый коммит требует актуализации записи.

## После merge и при регрессии

Автор проверяет CI итогового коммита и smoke-тест; для выпуска отдельно проверяются целевая ОС, архив и отсутствие закрытых данных. Сохраните прежний рабочий выпуск. Откат оформляйте новым revert-коммитом и PR в соответствующую ветку, не переписыванием истории. После регрессии добавьте воспроизводящий тест и уточните правило, которое должно было её обнаружить.

В локальном журнале отмечайте число раундов ревью, подтверждённые и ложные замечания, пропущенные проверки и необходимость отката. Если процесс требует больше внимания или пропускает регрессии, меняйте конкретную проверку, а не добавляйте повторные ревью без причины.
